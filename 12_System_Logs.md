
# 12. Linux System Logs

## Description

Linux system logs record events generated by the operating system, kernel, services, applications, and security-related components. These records help administrators understand system behavior, troubleshoot failures, investigate suspicious activity, and monitor security events.

For cybersecurity professionals, log analysis is a fundamental skill used in security monitoring, incident response, threat hunting, and digital forensics.

**Learning objectives:**

- Understand Linux logging architecture.
- Explore `journalctl`, `syslog`, and authentication logs.
- Investigate login attempts and service failures.
- Search logs using `grep`, `awk`, and related commands.
- Understand log rotation, retention, and permissions.
- Detect suspicious patterns and investigate security incidents.
- Perform practical log-analysis exercises in a Linux VM.

---

## 1. What Are Linux System Logs?

### Professional Definition

System logs are records of events generated by operating-system components, applications, services, and security mechanisms during system operation.

### Simple Explanation

Linux creates records of important events so administrators can understand what happened on a system.

Examples include:

- A user logging in.
- An SSH authentication failure.
- A service starting or stopping.
- A kernel error.
- A scheduled task executing.
- A disk becoming full.
- An application reporting an error.

### Why Are Logs Important in Cybersecurity?

Logs help security analysts:

- Investigate unauthorized access.
- Detect repeated failed login attempts.
- Identify suspicious process activity.
- Investigate service crashes.
- Reconstruct timelines of security incidents.
- Verify whether an administrative action occurred.
- Support compliance and auditing requirements.

**Important:** Logs provide evidence, but they are not always complete or trustworthy. An attacker with sufficient privileges may alter local logs, and a missing event does not prove that an activity never happened.

## 2. Understanding Linux Logging Architecture

Linux systems may use several logging components.

### A. Kernel Logging

The Linux kernel generates messages about hardware, drivers, system events, and other kernel-level activity.

Useful command:

```bash
dmesg
```

### B. systemd Journal

On systems using systemd, `systemd-journald` collects and stores journal entries from sources such as the kernel, services, and applications.

Useful command:

```bash
journalctl
```

### C. Syslog Implementations

Tools such as `rsyslog` and `syslog-ng` can collect, filter, and forward log messages.

Depending on configuration, they may write events to files such as:

- `/var/log/syslog`
- `/var/log/messages`
- `/var/log/auth.log`
- `/var/log/secure`

These paths are distribution- and configuration-dependent.

### D. Application Logs

Applications and services may maintain their own logs.

Examples include web server access logs, web server error logs, database logs, and application-specific audit records.

### Basic Logging Flow

```text
Kernel / Services / Applications
                |
                v
     Logging Components
                |
        +-------+-------+
        |               |
        v               v
   System Journal   Log Files
        |               |
        +-------+-------+
                |
                v
      Analysis and Monitoring
                |
                v
     Investigation and Response
```

The exact flow depends on the Linux distribution and logging configuration. Not every event is necessarily written to every destination.

## 3. Important Linux Log Locations

| Path | Common purpose |
|---|---|
| `/var/log/` | Common directory for log files |
| `/var/log/syslog` | General system messages on many Debian-based systems |
| `/var/log/messages` | General system messages on some distributions |
| `/var/log/auth.log` | Authentication-related messages on many Debian-based systems |
| `/var/log/secure` | Authentication-related messages on some Red Hat-based systems |
| `/var/log/kern.log` | Kernel messages on some systems |
| `/var/log/dpkg.log` | Package-management activity on Debian-based systems |
| `/var/log/apt/` | APT package-management logs |
| `/var/log/cron` | Cron-related messages on some systems |
| `/var/log/wtmp` | Binary login-session history database |
| `/var/log/btmp` | Binary failed-login record database, where configured |
| `/var/log/lastlog` | Per-user last-login information, where supported |
| `/var/log/audit/` | Audit logs when Linux Audit is configured |

**Important:** Not every distribution creates all these files. Systems may send messages exclusively or primarily to the systemd journal, or use a different logging configuration.

Check the available log files:

```bash
ls -lah /var/log/
```

Inspect the directory without modifying its contents.

## 4. The `journalctl` Command

`journalctl` is the primary command-line utility for querying the systemd journal.

### Display Journal Entries

```bash
journalctl
```

### Show the Most Recent Entries

```bash
journalctl -n 50
```

Displays the latest 50 journal entries.

### Follow Logs in Real Time

```bash
journalctl -f
```

Press `Ctrl+C` to stop following.

### Display Entries from the Current Boot

```bash
journalctl -b
```

### Display Entries from the Previous Boot

```bash
journalctl -b -1
```

This works only if the relevant previous-boot journal entries are available.

### Show Recent Errors

```bash
journalctl -p err
```

This filters by error priority and more severe levels. It does not show every possible operational problem.

### Filter by Time

```bash
journalctl --since "1 hour ago"
```

```bash
journalctl --since today
```

```bash
journalctl --since "2026-10-22 09:00:00" --until "2026-10-22 10:00:00"
```

Use timestamps appropriate to your investigation and system time zone.

### Show Logs for a Service

```bash
journalctl -u ssh
```

On some systems, the SSH service is named `sshd`.

Check both names if necessary:

```bash
systemctl status ssh
systemctl status sshd
```

Only one of these service names may exist on a particular system.

### Follow a Service's Logs

```bash
journalctl -u ssh -f
```

This is useful when troubleshooting SSH service activity in real time.

## 5. Understanding Log Priorities

The systemd journal and syslog commonly use these severity levels.

| Priority | Name | Meaning |
|---:|---|---|
| 0 | Emergency | System is unusable |
| 1 | Alert | Immediate action is required |
| 2 | Critical | Critical condition |
| 3 | Error | Error condition |
| 4 | Warning | Warning condition |
| 5 | Notice | Significant but normal condition |
| 6 | Informational | Informational message |
| 7 | Debug | Debugging information |

### Filter by Priority

Show errors and more severe priorities:

```bash
journalctl -p err
```

Show warnings and more severe priorities:

```bash
journalctl -p warning
```

Show only messages at informational priority:

```bash
journalctl -p info
```

Priority filtering is useful for narrowing down large volumes of logs, but a lower-priority event may still be security-relevant.

## 6. Authentication Logs

Authentication logs can record login attempts, authentication failures, session activity, and related events.

These logs are particularly important when investigating possible unauthorized access.

### Inspect Common Authentication Log Files

On many Debian-based systems:

```bash
sudo less /var/log/auth.log
```

On some Red Hat-based systems:

```bash
sudo less /var/log/secure
```

The file may not exist on your distribution.

### Search for Failed Authentication

```bash
sudo grep -i "failed" /var/log/auth.log
```

Search for invalid usernames:

```bash
sudo grep -i "invalid user" /var/log/auth.log
```

Search for successful SSH authentication messages:

```bash
sudo grep -i "accepted" /var/log/auth.log
```

These examples assume that the authentication log exists and that SSH messages are recorded there.

### Use the Journal Instead

```bash
sudo journalctl -u ssh --since today
```

Or, where the service uses the `sshd` unit:

```bash
sudo journalctl -u sshd --since today
```

### What Should You Investigate?

Look for:

- Repeated failures for the same account.
- Attempts involving many different usernames.
- Successful logins following repeated failures.
- Login activity at unexpected times.
- Unexpected privileged-account sessions.
- Unfamiliar source IP addresses.
- Authentication activity inconsistent with normal operations.

A single failed login is not proof of an attack. Investigate event frequency, source, context, and subsequent activity.

## 7. Login History Commands

Linux provides several utilities for examining login-related records.

### A. `who`

```bash
who
```

Displays information about users currently logged in through recorded sessions.

### B. `w`

```bash
w
```

Displays logged-in users and information about their current activity.

### C. `last`

```bash
last
```

Reads login-session history, commonly from `/var/log/wtmp`.

Show a limited number of records:

```bash
last -n 20
```

### D. `lastb`

```bash
sudo lastb
```

Reads failed-login records, commonly from `/var/log/btmp`, where available.

### E. `lastlog`

```bash
lastlog
```

Displays last-login information where the utility and its underlying records are supported.

**Important:** These tools rely on particular record sources. Their output may be incomplete, unavailable, or affected by local configuration and record retention.

## 8. Kernel Logs with `dmesg`

The `dmesg` command displays kernel ring-buffer messages.

### Display Kernel Messages

```bash
dmesg
```

### Show Human-Readable Timestamps

```bash
dmesg -T
```

Human-readable timestamp conversion can be inaccurate across some time changes or suspend/resume scenarios. Use authoritative timestamps when constructing incident timelines.

### Search for Errors

```bash
dmesg --level=err,warn
```

### Follow Kernel Messages

```bash
dmesg --follow
```

### What Can Kernel Logs Reveal?

- Device or driver errors.
- Hardware problems.
- Storage failures.
- Kernel warnings.
- Some hardware or system initialization events.

Kernel logs are not a complete security audit trail. They should be correlated with service, authentication, and application logs.

## 9. Search Logs with `grep`

`grep` searches text for matching patterns.

### Search for a Keyword

```bash
grep "error" application.log
```

### Ignore Case

```bash
grep -i "failed" application.log
```

### Display Line Numbers

```bash
grep -n "authentication failure" application.log
```

### Search Multiple Patterns

```bash
grep -Ei "failed|invalid user|authentication failure" application.log
```

### Search Recursively

```bash
grep -Rni "error" /path/to/authorized/logs/
```

### Show Context Around a Match

```bash
grep -C 3 "failed password" application.log
```

This displays three lines before and after each matching line.

### Count Matching Lines

```bash
grep -ic "failed password" application.log
```

This counts matching lines, not necessarily unique login attempts or unique source addresses.

### Cybersecurity Use Case

Search logs for suspicious authentication patterns, error messages, or application events. Then investigate the surrounding records to understand the sequence of activity.

Avoid assuming that a text match automatically represents malicious behavior.

## 10. Analyze Logs with `awk`, `sort`, and `uniq`

These utilities help summarize and investigate structured or semi-structured text logs.

### A. Display Specific Fields

```bash
awk '{print $1, $2, $3}' application.log
```

This prints the first three whitespace-separated fields.

### B. Count Repeated Values

For a sample file where each line contains one IP address:

```bash
sort sample_ips.txt | uniq -c | sort -nr
```

This counts repeated IP addresses and displays the most frequent entries first.

### C. Count Matching Authentication Messages

```bash
grep -i "failed password" sample_auth.log | wc -l
```

This counts lines containing the specified phrase.

### D. Extract IPv4-Like Strings for Review

```bash
grep -Eo '([0-9]{1,3}\.){3}[0-9]{1,3}' sample_auth.log
```

This extracts strings matching a basic IPv4-like pattern. It does not validate that each result is a valid IPv4 address.

### Important Limitation

Linux log formats differ. Field positions, delimiters, timestamps, and message formats may vary. Always inspect the input before writing field-based analysis commands.

## 11. Log Rotation

Log rotation prevents log files from growing indefinitely and consuming available disk space.

Many Linux systems use `logrotate` for this purpose.

### Check Whether Logrotate Is Available

```bash
command -v logrotate
```

### Inspect Its Configuration

```bash
less /etc/logrotate.conf
```

Check additional rules:

```bash
ls -lah /etc/logrotate.d/
```

### Common Logrotate Directives

| Directive | Purpose |
|---|---|
| `daily` | Rotate daily |
| `weekly` | Rotate weekly |
| `monthly` | Rotate monthly |
| `rotate 7` | Retain seven rotated copies |
| `compress` | Compress rotated logs |
| `missingok` | Do not report an error when the log is missing |
| `notifempty` | Do not rotate an empty log |
| `create` | Create a replacement log file with specified settings |

Actual behavior depends on the configuration and the log file's requirements.

### Why Log Rotation Matters in Security

- Preserves recent evidence while managing storage.
- Reduces the risk of a disk filling up.
- Supports a defined retention policy.
- Makes log management more predictable.

**Security note:** Rotation is not the same as secure archival. Important investigation records may need protected storage, integrity controls, centralized collection, and a retention policy appropriate to organizational and legal requirements.

## 12. Log Permissions and Protection

Logs can contain usernames, IP addresses, system details, session activity, and other sensitive information.

### Inspect Permissions

```bash
ls -l /var/log/
```

Inspect a specific file:

```bash
stat /var/log/auth.log
```

Use the actual file available on your system.

### Security Best Practices

1. Restrict log access to authorized users.
2. Avoid making sensitive logs world-readable without a valid reason.
3. Protect log directories and their parent directories.
4. Use centralized logging for important systems where appropriate.
5. Monitor changes to logging configurations.
6. Define retention and secure disposal requirements.
7. Synchronize system clocks to improve timeline accuracy.
8. Avoid storing secrets in application logs.
9. Preserve original records during incident investigations.
10. Use appropriate integrity controls for critical audit data.

Do not arbitrarily change permissions on system logs. Logging services may require particular ownership, permissions, or access-control settings.

## 13. Centralized Logging

Centralized logging collects events from multiple systems into a shared logging platform.

### Why It Is Useful

- Allows analysts to investigate several systems together.
- Supports correlation of related events.
- Reduces dependence on a single machine's local logs.
- Helps preserve records if an endpoint is compromised.
- Enables broader monitoring and alerting.

### Typical Architecture

```text
Linux Server A ----+
                   |
Linux Server B ----+----> Central Log Server
                   |              |
Linux Server C ----+              v
                            Search and Analysis
                                   |
                                   v
                           Alerts / Investigation
```

Common solutions include:

- `rsyslog`
- `syslog-ng`
- Elastic Stack
- Wazuh
- Splunk

Select a platform based on operational requirements, retention needs, scale, and security controls.

### Security Considerations

- Encrypt log transport where supported.
- Authenticate log senders.
- Restrict access to the central logging platform.
- Protect stored records against unauthorized changes.
- Monitor ingestion failures and missing data.
- Synchronize clocks across systems.
- Avoid treating a centralized platform as automatically tamper-proof.

## 16. Practical Lab 3: Detect Repeated Failed-Login Patterns

### Objective

Create a simple script that analyzes a synthetic authentication log.

Create the script:

```bash
nano "$HOME/log_lab/failed_login_report.sh"
```

Add:

```bash
#!/usr/bin/env bash

set -u

log_file="${1:-$HOME/log_lab/sample_auth.log}"

if [[ ! -r "$log_file" ]]; then
    echo "Error: Log file is missing or unreadable: $log_file" >&2
    exit 1
fi

echo "===== FAILED LOGIN REPORT ====="
echo "Timestamp: $(date)"
echo "Input file: $log_file"
echo

echo "Total matching failed-login lines:"

if grep -icE 'failed password|authentication failure|invalid user' "$log_file"; then
    :
else
    status=$?

    if [[ "$status" -ne 1 ]]; then
        echo "Error: Log search failed." >&2
        exit "$status"
    fi
fi

echo
echo "Matching events:"
grep -inE 'failed password|authentication failure|invalid user' "$log_file" || true

echo
echo "===== REPORT COMPLETE ====="
```

Make it executable:

```bash
chmod 700 "$HOME/log_lab/failed_login_report.sh"
```

Run it:

```bash
"$HOME/log_lab/failed_login_report.sh"
```

Or specify a different authorized log:

```bash
"$HOME/log_lab/failed_login_report.sh" "$HOME/log_lab/sample_auth.log"
```

### What This Script Demonstrates

- Input validation.
- File readability checks.
- Pattern-based searching.
- Basic error handling.
- Repeatable report generation.

### Limitation

This script counts matching lines, not unique authentication attempts. A line may contain several relevant terms, and actual log formats vary. For production investigations, use structured parsing and validate the results against the original records.

## 18. Incident Response: A Structured Log Investigation

When a potential security incident is identified, follow a consistent workflow.

### Step 1: Define the Scope

Identify the affected system, relevant service, suspected activity, and time range.

### Step 2: Collect Relevant Records

Use the system journal, authentication logs, application logs, and other authorized sources.

### Step 3: Preserve Evidence

Preserve original records where possible. Document collection times, sources, and any transformations applied during analysis.

### Step 4: Build a Timeline

Correlate timestamps from multiple sources. Account for time zones, clock drift, and differences in timestamp formats.

### Step 5: Search for Related Events

Look for authentication activity, process execution, service changes, network connections, and other events related to the investigation.

### Step 6: Assess Reliability

Consider whether logging was enabled, whether records are missing, and whether an attacker could have modified local evidence.

### Step 7: Respond According to Policy

Follow the organization's containment and escalation procedures. Avoid destructive changes that could destroy useful evidence.

### Step 8: Document Findings

Include observed facts, supporting records, limitations, actions taken, and recommendations.

## 19. Common Troubleshooting Problems

### Problem 1: `/var/log/auth.log` Does Not Exist

**Possible causes:**

- Your distribution uses another log path.
- Authentication events are recorded in the system journal.
- A traditional syslog service is not installed or configured.

**Solution:**

```bash
sudo journalctl -u ssh --since today
```

Check the appropriate service name and logging configuration.

### Problem 2: `journalctl` Shows No Previous Boot Logs

**Possible cause:** The system may not retain persistent journal data across reboots.

Inspect journal storage:

```bash
journalctl --list-boots
```

Check the journald configuration and storage setup before changing anything.

### Problem 3: Permission Denied

**Possible causes:**

- The log is restricted to privileged users.
- File permissions or access-control rules prevent access.

**Solution:** Use authorized privileges when appropriate and follow local access policies. Do not weaken log permissions merely to make a command work.

### Problem 4: Logs Are Missing

**Possible causes:**

- Logging was disabled or misconfigured.
- The relevant service did not generate the event.
- Records were rotated or expired.
- A different logging source is being used.
- The system clock or time filter is incorrect.

**Solution:** Check time ranges, logging configuration, service status, retention, and other available data sources.

### Problem 5: Too Many Log Entries

**Solution:** Narrow the investigation using:

```bash
journalctl --since "1 hour ago" -p warning
```

For files:

```bash
grep -i "failed" /var/log/auth.log | tail -n 50
```

Replace the example log path if necessary.

### Problem 6: A Log File Is Very Large

Avoid opening enormous files in editors unnecessarily. Use targeted searches, `tail`, time filters, and appropriate streaming tools.

### Problem 7: Timestamps Do Not Match

Check the system clock and time zone:

```bash
timedatectl
```

When comparing records across multiple systems, normalize timestamps and account for clock drift.

## 20. Best Practices for Linux Log Management

1. Enable appropriate logging for important services.
2. Monitor authentication and privilege-related events.
3. Restrict access to logs.
4. Configure suitable rotation and retention.
5. Protect important records against unauthorized modification.
6. Forward critical logs to a centralized platform when appropriate.
7. Monitor logging failures and ingestion gaps.
8. Synchronize system clocks.
9. Avoid recording passwords, tokens, and unnecessary sensitive information.
10. Preserve original records during investigations.
11. Document the log sources and queries used in incident reports.
12. Correlate events instead of treating individual messages as conclusive proof.
13. Test alerting and log collection regularly.
14. Verify that retention meets operational, regulatory, and legal requirements.

## 22. Interview Questions and Answers

### Q1. What are Linux system logs?

Linux system logs are records of events generated by the operating system, services, applications, and security components. They are used for monitoring, troubleshooting, auditing, and investigations.

### Q2. What is `journalctl`?

`journalctl` is the command-line utility used to query and inspect entries stored in the systemd journal.

### Q3. Where are Linux logs stored?

Many Linux systems store log files under `/var/log/`, while systems using systemd may also store events in the journal. Exact locations depend on the distribution and configuration.

### Q4. What is the difference between `syslog` and `journald`?

Syslog is a logging interface and ecosystem of protocols and implementations. `systemd-journald` is a systemd logging service that collects and stores journal entries. Both may operate together.

### Q5. How do you check failed SSH login attempts?

Inspect the configured authentication log or query the SSH service journal using an appropriate time filter.

Example:

```bash
sudo journalctl -u ssh --since today
```

The service name may be `sshd` on some systems.

### Q6. What does `journalctl -f` do?

It follows journal entries as new events arrive, making it useful for real-time troubleshooting and monitoring.

### Q7. What is log rotation?

Log rotation manages growing log files by rotating, compressing, and retaining records according to a configured policy.

### Q8. Why are logs important in incident response?

They provide evidence about authentication, service activity, system events, and application behavior. Correlating logs can help reconstruct an incident timeline.

### Q9. Can logs be modified by attackers?

Yes. An attacker with sufficient privileges may alter or delete local records. Centralized logging and protected storage can improve resilience, but their effectiveness depends on configuration and access controls.

### Q10. What is centralized logging?

Centralized logging collects records from multiple systems into a common platform for searching, monitoring, correlation, and retention.

### Q11. What is the difference between `last` and `lastb`?

`last` typically reads login-session history from `wtmp`. `lastb` typically reads failed-login records from `btmp`, where those records are available.

### Q12. How do you troubleshoot missing logs?

Check the correct log source, time range, service status, logging configuration, permissions, retention policy, and whether the event was actually generated.

### Q13. What is the purpose of `dmesg`?

It displays kernel ring-buffer messages, which can help diagnose kernel, hardware, and driver issues.

### Q14. Why is time synchronization important for security logs?

Accurate and consistent timestamps make it easier to correlate events across systems and construct reliable incident timelines.

### Q15. What is the difference between a log and an alert?

A log is a recorded event. An alert is a notification generated when a defined rule, threshold, or detection condition is met.

## 23. Scenario-Based Interview Questions

### Scenario 1: Multiple Failed SSH Logins

**Question:** You notice many failed SSH authentication attempts from one address. What do you do?

**Answer:**

1. Define the relevant time range.
2. Review authentication logs and source-address information.
3. Count events and identify targeted accounts.
4. Check whether any authentication succeeded.
5. Correlate related service and system activity.
6. Verify whether the source is expected or authorized.
7. Escalate or contain the activity according to policy.

Repeated failures can indicate password guessing, but additional evidence is needed to establish what happened.

### Scenario 2: Successful Login After Repeated Failures

**Question:** Is this automatically a successful brute-force attack?

**Answer:**

No. It is a potentially significant sequence that needs investigation. Verify the account, source, authentication method, surrounding events, and whether the session performed any suspicious actions.

### Scenario 3: Logs Suddenly Stop Arriving

**Question:** What might have happened?

**Answer:**

Possible causes include a stopped logging service, network failure, full disk, configuration changes, retention issues, or deliberate interference. Check both the source system and the log collection platform.

### Scenario 4: A Privileged User Deletes Logs

**Question:** What would you do?

**Answer:**

Preserve remaining evidence, identify the scope of missing records, inspect available audit and centralized logs, establish a timeline, and follow incident-response procedures. Avoid making unsupported conclusions based only on the absence of records.

## 24. Quick Revision Notes

- **System logs:** Records of operating-system, application, and security events.
- **`/var/log/`:** Common location for text-based log files.
- **`journalctl`:** Query systemd journal entries.
- **`journalctl -f`:** Follow new journal entries.
- **`journalctl -b`:** Show entries from the current boot.
- **`dmesg`:** Display kernel ring-buffer messages.
- **`grep`:** Search for patterns.
- **`awk`:** Extract or process text fields.
- **`sort` and `uniq`:** Organize and count repeated values.
- **`last`:** Display recorded login-session history.
- **`lastb`:** Display failed-login history where supported.
- **Log rotation:** Manage log size and retention.
- **Centralized logging:** Collect events from multiple systems.
- **Incident timeline:** A chronological reconstruction of relevant events.
- **Log integrity:** Protection against unauthorized modification or deletion.
